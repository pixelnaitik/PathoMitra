### Two corrections to the beliefs this project has been operating on

Both are load-bearing enough that they change the recommended path, so they are stated up front.

**C-1 — "Microsoft Store is off the table because electron-builder 26.x cannot build MSIX" is only half true.**
The Store accepts **`.appx` / `.appxbundle` / `.appxupload`** as well as `.msix*` (official "App package
requirements for MSI/EXE app" FAQ, fetched today), and electron-builder 26.15.3 **does** implement the `appx`
target (`electron-builder.config.mjs:14-17` records that only `msix` is unknown). The `appx` block is already
configured (`:80-92`). Furthermore `makeappx.exe` **and** `signtool.exe` are present on this machine at
`C:\Program Files (x86)\Windows Kits\10\bin\10.0.26100.0\{x64,arm64,x86}\`. So a Store-ingestible container is
plausibly buildable **today** — unproven, because no `appx` build has ever been run. This does not erase the
LocalCache argument (§P-04) or the `runFullTrust` argument (§Cap-08); it means the decision is now a real choice
rather than a blocked one.

**C-2 — "MSI is not accepted by the Store" (recorded in `promotion_website/STORE-READINESS-REPORT.md:258`) is wrong.**
Policy **10.2.9** and the MSI/EXE submission docs (fetched today) accept an HTTPS versioned download URL to an
`.msi`/`.exe`; EXE/MSI submission has been allowed since June 2021. The blocker is not the container — it is
**the signing requirement, which reads "the binary _and all of its Portable Executable (PE) files_".**
Measured today: **16 of 18 PEs in `win-unpacked` are not validly signed** (`Get-AuthenticodeSignature`, this session):

